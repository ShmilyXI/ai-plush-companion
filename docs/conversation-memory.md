# 角色的记忆

网页对话里，角色会记住关于用户的事，下次聊天还记得。本文记录它是怎么记、怎么用、用户怎么管，以及它的局限。

## 以前的情况

在这之前，网页端的角色用的记忆设置是“无记忆”（`Memory_nomem`）。角色能接上之前的话，靠的只是每次对话开始时取回来的最近若干轮对话记录，更早的内容它不知道。

现有的几种记忆实现（`mem_local_short`、`mem0ai`、`tencentdb` 等）是为实体设备设计的，按设备的地址找配置和存储位置，管理接口也是按设备划分的，网页对话接不上。所以这里另做了一套简单的。

## 怎么记

每一轮对话说完、已经记进对话记录之后，对话服务在后台多调用一次大模型，把用户刚说的话交给它，让它挑出以后还用得上的事实，写成一句句简短的话，例如“用户养了一只叫年糕的猫”。

- 这一步在后台进行，不影响回复和语音的速度。
- 用户这句话太短（不到 6 个字）或者只有标点时不提炼，省一次模型调用。
- 提示词要求不记寒暄和一时的情绪、不记猜测、不记证件号和密码这类信息。这只是对模型的要求，不是保证。
- 已经记得的事不重复记：对话服务先比对一遍，manager-api 保存时再比对一遍，比对时不看空白和标点。
- 模型的输出格式不对、保存失败时什么都不记，对话照常进行。

记下的事存在 manager-api 的 `ai_conversation_memory` 表里，按“用户 + 角色”保存。每条最长 200 个字，每个角色最多 60 条，记满后丢掉最早的。

只有登录用户的对话有记忆，和对话记录是同一个开关。用 API Key 接入的第三方背后是很多不同的终端用户，他们的事不能记在一起，所以不记。

## 怎么用

对话开始时，对话服务把这个角色记得的事取回来，写在提示词里角色设定的后面、平台安全守则的前面，并要求模型自然地用上、不要逐条复述。同一次对话里新记下的事，下一轮就带上。

同时放进提示词的还有两样：角色自己的名字（用户自建的角色提示词里不一定写了）和用户希望被怎么称呼。

## 用户怎么管

在网页端的角色设置里有一栏“它记得的事”：

- 逐条删除，或者全部忘掉。
- 自己写一条让它记住。
- 这里的改动立刻保存。正在进行的对话不会马上知道，下一次开始对话时生效。

另外两个入口也会清掉记忆：清空和某个角色的对话记录时，这个角色记得的事一起清掉；注销账号时全部删除。

## 接口

对话服务用的（需要服务间密钥）：

- `GET /internal/public-conversations/{conversationId}/memories`
- `POST /internal/public-conversations/{conversationId}/memories`，内容是 `{"items": ["…"]}`

登录用户用的：

- `GET /api/v1/conversations/threads/{agentId}/memories`
- `POST /api/v1/conversations/threads/{agentId}/memories`，内容是 `{"content": "…"}`
- `DELETE /api/v1/conversations/threads/{agentId}/memories/{memoryId}`
- `DELETE /api/v1/conversations/threads/{agentId}/memories`

## 局限

- **会记错。** 事实是模型提炼的，可能理解错、记下不重要的事，或者漏掉重要的事。没有评估过提炼的质量。
- **每轮多一次模型调用**，成本会增加，具体增加多少没有测过。没有做成“攒几轮再提炼”。
- **不会更新旧的事实。** 用户说“我的猫去年走了”，它会新记一条，但不会删掉“用户养了一只猫”。两条都在，由用户自己删。
- **全部带进对话。** 最多 60 条一起放进提示词，没有按话题挑选相关的。
- **明文保存**，和对话记录一样。
- **设备对话不用这套记忆**，仍然用各自配置的记忆实现。同一个角色在设备上和网页上记得的事不相通。
