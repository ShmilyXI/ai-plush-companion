# 打开即跟进：角色先开口

用户隔了一段时间再回来，看到的不应该是一个空白的输入框。角色会先说一句话：之前聊过的事里有值得接着问的，就问一句后来怎么样了；没有的话打个招呼。第一次见面也由角色先开口。

## 什么时候开口

由服务端决定，网页端只负责在进入页面后请求一次。

| 情况 | 结果 |
|---|---|
| 从来没聊过 | 开口，打个招呼，问一个容易回答的小问题 |
| 距离上一句话超过设定的间隔 | 开口，接着之前的话题问一句 |
| 距离上一句话不到设定的间隔 | 不开口。用户只是刷新了页面或断线重连 |
| 用户已经先说话了 | 不开口 |
| 之前的对话记录没取回来 | 不开口。这时分不清是不是第一次见面 |
| 今天的对话次数已经用完 | 不开口 |
| 通过 API Key 接入的对话 | 不开口。这类对话不保存“用户 + 角色”的记录 |

间隔由系统参数 `app.opening_gap_hours` 决定，默认 4 小时，在管理台的“参数管理”里修改，设为 0 表示关闭这个功能。

一个会话只理会第一次请求。开场白说完会写进对话记录，“上一句话的时间”随之更新，所以紧接着再打开不会重复。

## 说什么

说什么由模型决定。服务端给它的是场合：现在是几月几日周几、什么时段，距离上次聊天过去了多久，以及最近的对话。要求是一两句话、不超过 40 个字、只挑一件事问、不复述上次的内容；如果用户上次情绪很低落，先关心他现在好不好，不追问细节。这段说明在 `core/public_conversation/opening.py`，它不进对话记录，用户看不到。

开场白和普通回复一样经过内容安全检查，也会合成语音。浏览器在用户还没有任何操作时通常不允许播放声音，这时只显示文字，可以点“重听”。

## 它不算用户的一轮

- 不占每日对话次数，不计入单个会话的轮数上限。
- 用量照常记录（token、合成字数），输入方式记为 `opening`。管理台“对话用量”页面单独有一列“开场白”，对话轮数和活跃用户只算用户发起的对话。
- 留存和首字耗时的统计不包含开场白：用户只是打开页面、没有说话，不算活跃。
- 不写入长期记忆。

## 失败的时候

开场白是角色主动说的，用户没有在等它。模型出错、超时、内容被收回时，这一轮安静地结束（`turn.cancelled`，原因是 `opening_failed`），已经显示的文字被拿掉，用户不会看到错误提示，可以照常说话。

## 协议

客户端在实时连接就绪后发送：

```json
{"type": "conversation.opening", "request_id": "<唯一标识>"}
```

需要开口时，服务端发出一轮普通的事件：`turn.started`（`input_mode` 是 `opening`）、`llm.delta`、`tts.audio.chunk`、`turn.completed`（`details.opening` 是 `true`）。不需要开口时没有任何回应。

对话记录接口返回的条目里，开场白的 `text` 是空字符串，并带 `opening: true`。客户端只显示角色这一边。给模型的上下文里，开场白前面用一句“（用户打开了页面，还没有说话）”占住用户的位置，保证用户和助手的消息交替出现。

## 还没做的

- 开场白只在打开页面时出现。不在页面上的时候不会有推送或提醒。
- 没有按用户关闭的开关，只有全局的间隔参数。
- 开场白的效果（用户有没有接话）还没有单独的统计，可以从用量表里 `opening` 之后有没有紧跟着用户的一轮算出来。
