# TencentDB 记忆召回与积压恢复设计

## 背景

当前 `xiaozhi-server` 运行在 Python 3.10。TencentDB Memory Provider 使用 Python 3.11 才提供的 `asyncio.timeout`，导致 L1、L2、L3 三层召回在创建超时上下文时立即抛出 `AttributeError`。异常被现有降级逻辑转换为空记忆，因此设备调试页显示查询完成且耗时接近零，但实时模型没有得到任何记忆内容。

MemoryCore 已持久化真实设备的 L0 原始对话。长会话由 MemoryCore 每次最多提炼前十条消息，剩余消息依赖十分钟空闲定时器继续处理。容器在定时器触发前重启时，尚未提炼的后半段仍保留在 L0，但不会立即进入 L1。用户姓名“潇潇”属于这批未完成提炼的消息。

## 目标

召回逻辑必须兼容项目当前的 Python 3.10 运行时。已有 L1 记忆在服务重启后可以正常召回，失败或超时时仍保持无记忆降级，不阻塞实时对话。

新保存的长会话不能依赖 MemoryCore 进程内的长时间空闲定时器才能处理后半段。全部消息需要在会话保存阶段进入可独立提炼的批次，同时保留用户、角色和来源设备隔离。

已经持久化在 L0 的姓名信息需要通过一次受控重放重新进入提炼流程。重放使用用户真实说过的内容，不编造或修改记忆正文。

## 召回兼容

`MemoryProvider._with_layer_timeout` 改用 `asyncio.wait_for`。它在 Python 3.10 和后续版本均可用，并保持每层三秒超时、单层失败不影响其他层、所有层失败时返回空字符串的现有行为。

回归测试会暂时移除 `asyncio.timeout` 属性，模拟 Python 3.10 环境。测试使用真实协程验证 L1、L2、L3 均被等待执行，查询结果包含召回内容，且不产生未等待协程警告。另一个测试验证超时仍被记录为对应层降级。

## 长会话保存

Provider 在写入 MemoryCore 前把超过十条的消息按原顺序切成最多十条的批次。单批会话继续使用原 session ID。多批会话使用稳定的分片 session ID，第一批保留原 ID，后续批次增加只由原 session ID 和批次序号组成的后缀。每个批次继续携带相同的用户、角色和设备来源。

每批沿用现有不确定写入处理。请求结果不明确时，只检查当前分片 session 的尾部并决定是否重试，避免跨批次误判。十条以内的现有行为和 session ID 保持不变。

分片让 MemoryCore 为每批建立独立提炼任务，不再依赖单个会话的十分钟积压定时器。召回和后台记忆列表按用户与角色查询，不依赖原始 session ID，因此分片不会改变共享和隔离语义。

## 存量姓名恢复

部署修复后，从 MemoryCore 读取当前用户与角色下已经持久化的 L0，确认存在用户原话“我叫潇潇”。随后用独立恢复 session 重放该条用户消息和对应的助手确认消息，保留原设备来源。等待 L1 生成并验证原子记忆包含用户姓名。

恢复操作只针对这次已确认的积压数据，不提供通用自动重放任务，避免旧对话被重复提炼。生成完成后重启 `xiaozhi-server`，使用“我是谁”执行真实召回，结果必须包含姓名记忆。

## 验证

Python 单元测试覆盖 Python 3.10 超时兼容、三层并发召回、单层超时降级、十条以内写入、多批分片、分片重试与设备来源传播。

本地容器验收会验证现有 L1 在修复后可被 `query_memory` 返回，存量姓名重放后生成 L1，`xiaozhi-server` 重启后姓名仍存在，后台记忆列表可见，并且设备调试事件不再出现零毫秒的三层 `AttributeError` 降级。

## 回滚

代码回滚只恢复 Provider 文件，不修改 MemoryCore volume。已经生成的姓名 L1 会继续保留。若分片行为需要回滚，十条以内会话不受影响，长会话恢复为 MemoryCore 自身的积压定时处理。
