# 公共对话网页语音播放设计

## 目标

公共对话网页在保留流式文字回复的同时，自动播放服务端 `tts.audio` 事件携带的语音。改动只属于浏览器参考客户端，不修改 Java 会话接口、Python WebSocket 协议或设备 MQTT 链路。

## 数据流

网页创建会话时继续声明 `outputModes: ["text", "audio"]`。Python 运行时完成 TTS 后返回 `tts.audio`，其中包含 MIME 类型和 base64 音频。网页把音频转换成 Blob URL，并按事件到达顺序加入单一播放队列。当前音频播放结束后释放 Blob URL，再播放下一段，避免多段语音重叠。

当前协议默认通过 JSON 返回音频，因此本次先消费 `tts.audio`。浏览器适配器已有的 `tts.audio.binary` 能力继续保留，但不在这个页面改动中切换传输模式。

## 页面行为

收到文字增量时照常更新回复气泡。收到音频时开始或排队播放，不额外增加音频卡片。播放期间连接保持可发送状态。新一轮回复到达时继续排队，保证服务端事件顺序不变。

浏览器拒绝自动播放时，文字回复不受影响，连接状态显示需要点击页面开启声音。用户下一次点击页面时恢复播放队列。无法识别的 MIME 类型、无效 base64 或媒体播放失败只终止对应音频，不关闭 WebSocket，也不影响后续对话。

连接关闭、会话过期或页面卸载时停止当前音频，清空等待队列并释放所有 Blob URL，避免旧会话语音在重连后继续播放。

## 验证

浏览器行为测试从页面公开界面和媒体调用观察结果，确认 `tts.audio` 会被消费、多段音频顺序播放、失败后文字仍可见、连接关闭时资源被回收。真实联调使用当前紫萱角色发送一条短消息，确认页面出现文字回复，收到 TTS 事件，并由浏览器发起媒体播放。自动播放策略由真实浏览器验证，测试环境不伪造用户授权结果。
