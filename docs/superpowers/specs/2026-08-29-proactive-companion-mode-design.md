# 主动陪伴模式设计

## 文档目的

为设备增加可持久化的陪伴模式设置，并在主动模式下支持持续在线、噪声过滤、用户活动检测、空闲规划和主动语音。默认行为保持现有对答模式，只有设备被明确设置为主动陪伴后才启用主动流程。

本设计覆盖 ESP32 固件、MQTT 网关、Python `xiaozhi-server`、Java `manager-api` 和 `companion-console`。它不改变 Skill 的授权边界，也不把主动陪伴实现成 Skill。

## 模式定义

设备级字段 `companion_mode` 使用字符串值 `turn_based` 和 `proactive`，数据库默认值为 `turn_based`。`turn_based` 是当前的一问一答模式，设备在用户输入后生成回复，播放完成后等待下一次输入。`proactive` 保持连接和实时收音，在用户长时间没有确认活动时，允许服务端自主规划并发起短消息。

模式属于设备设置，不属于 Agent 版本。设备切换角色时继续保留自己的模式。设备连接建立时读取一次有效模式，当前连接内不热切换；后台修改后通过配置版本或重新连接生效。管理员界面显示当前保存值和最近一次下发状态，不把保存成功误认为设备已经在线应用。

## 管理端改动

`ai_device` 增加 `companion_mode` 字段，使用可扩展的字符串列而不是数据库枚举。迁移将旧设备统一写入 `turn_based`，未知值在读取时按 `turn_based` 处理并记录校验日志。

管理员设备列表和设备详情返回 `companionMode`。管理员设备详情增加一个二选一控件，文案为对答模式和主动陪伴。模式保存使用独立接口 `PUT /admin/companion/devices/{deviceId}/mode`，请求体只有 `mode`，避免复用当前只支持修改别名的请求 DTO。接口校验设备存在、模式值合法并记录审计事件，事件内容只包含设备 ID、旧值和新值。

普通用户设备详情可以只读显示有效模式，是否允许用户修改不在本轮范围内。若以后开放用户修改，必须复用同一套模式校验和配置发布逻辑，不能在前端直接写设备配置。

## 配置下发

`CompanionConfigService` 在构建设备私有配置时加入 `mode`、`idle_first_check_ms`、`idle_backoff_min_ms`、`idle_backoff_max_ms` 和 `proactive_max_chars`。其中模式来自 `DeviceEntity`，陪伴规则和默认参数来自 Agent 或服务端全局配置。设备级模式优先于默认配置，明确的设备值不能被 Python 本地默认值覆盖。

Python 连接初始化时把设备模式合并到连接配置，并在连接日志中记录模式和配置版本。已有 `companion.enabled` 继续表示陪伴能力是否可用；主动模式必须同时满足 `companion.enabled=true` 和 `companion.mode=proactive`。能力未启用、模型不完整、设备不支持 AEC/realtime 或配置解析失败时，连接退回对答模式并记录可读原因。

## 音频活动判定

主动模式要求设备使用支持 AEC 的 realtime 监听方式。设备端继续负责采样、降噪、回声消除和本地 VAD，服务端继续接收音频并使用 Silero VAD。播放期间检测到确认的人声后，服务端取消当前主动 TTS 和规划任务，发送设备停止播放并进入用户监听状态。

用户活动不等于 ASR 文本。服务端维护独立的 `last_confirmed_user_activity`。连续的人声帧、能量变化和 VAD 状态转换足以确认活动，即使 ASR 最终为空，也要刷新活动时间并取消主动流程。因此嗯、啊、咳嗽和清嗓子都算用户活动，但不会自动触发 LLM 回复。

噪声过滤采用两级结果。短暂爆音、桌面碰撞、风声和扬声器回声被归类为噪声，不更新活动时间。经过 AEC 后仍呈现为人声、持续达到门槛或具有明显语音结构的声音归类为用户活动。VAD 需要使用双阈值、连续帧门槛和最小活动时长，具体数值通过真实设备验收校准。设备端和服务端都要保留 300 至 500 毫秒前滚缓冲，避免确认活动时丢掉开头音节。

普通对答模式保留现有半双工行为。主动模式使用 realtime+Aec；不支持 AEC 的设备不能被后台切成主动模式，界面应显示不支持原因，而不是保存一个设备无法执行的设置。

## 主动陪伴编排

每个 `ConnectionHandler` 持有一个 `CompanionLoop`，任务生命周期与 WebSocket 连接一致。状态依次为正常活动、空闲等待、主动规划、主动播放和用户接管。连接关闭、设备解绑、模式切换或异常退出时必须取消所有等待和 LLM 任务。

用户活动结束后启动首次空闲计时。达到阈值后创建一个可取消的主动规划任务。规划任务读取最近对话、近期记忆、未完话题和最近主动消息，向 LLM 请求结构化结果。结果只能选择保持安静或生成一句短消息，并包含互动类型、情绪和可播放正文。规划任务禁止调用设备工具和外部写操作。

规划任务使用连接级互斥，不能与普通 `chat` 同时修改同一个对话上下文。任务开始时记录活动代次 `activity_epoch`，生成完成后再次比较代次、模式、连接状态和播放状态。期间出现任意确认活动，结果直接丢弃。即使文本已经生成，只要播放前检查失败，也不能发送 TTS。

主动消息必须写入会话历史和 Memory，并标记 `source=proactive`。模型只能引用真实召回的上下文，找不到自然切入点时选择保持安静。首次主动检查和后续检查使用递增冷却与有限随机抖动，不采用固定周期话术。主动消息默认控制在一到两句和配置的字符上限内，不强制每次提问。

主动模式绕过普通的无声自动结束流程，但仍受连接令牌、网络心跳和服务端资源上限约束。长时间没有任何活动时，连接继续保活；是否停止主动陪伴由模式、设备离线、用户主动关闭或服务端资源策略决定。所有主动规划、取消、噪声判定和播放结果都写入脱敏调试事件，不记录原始音频和密钥。

## 提示词分层

系统提示词负责全局语言、长度、安全和输出格式。Agent 的 personality 负责角色口吻和关系距离。主动规划请求追加仅在 `proactive` 来源下生效的规则，要求少打扰、优先回应真实的近期情绪和未完话题、不重复固定问候、没有上下文就保持安静、不得编造共同记忆。

陪伴提示词与 Agent 系统提示词必须合并，不能互相覆盖。当前 `PromptManager` 在陪伴启用时会用 `persona_prompt` 替换原始 prompt，后续实现应改为固定规则、Agent 系统提示词、角色 personality 和主动模式规则的稳定拼接，并为各层增加测试。

主动规划使用独立的 `proactive_planner_prompt`，不直接把普通对答提示词当成规划指令。服务端固定规则负责安全、少打扰、禁止虚构记忆、禁止调用设备工具、保持结构化输出和长度上限。全局主动陪伴提示词在后台系统设置中统一维护，作为所有主动模式设备共享的公共指导；Agent 可以再提供可版本化的主动陪伴指导，例如偏好的互动距离、适合回访的话题类型和不希望主动触碰的主题，但两者都不能覆盖服务端固定规则。规划模型只能返回 `stay_silent` 或一条可播放短句；无自然切入点、上下文可信度不足或用户状态不明确时必须选择 `stay_silent`。

后台系统设置页增加主动陪伴提示词文本域，管理员可以读取、编辑和保存全局内容。后端沿用现有系统设置服务和审计链路，使用独立配置键保存，保留内置默认提示词作为空值回退。读取和保存只允许管理员，提示词内容不进入普通设备日志和审计详情。保存后递增配置版本并使 Python 配置缓存失效；已经建立的连接继续使用建立时的提示词快照，新连接读取新版本。

规划提示词的拼接顺序固定为服务端不可覆盖规则、后台全局主动陪伴提示词、Agent 主动陪伴指导、结构化输出约束和记忆上下文。记忆内容使用明确的上下文分隔标记，并被视为资料而不是指令，防止历史文本反过来修改规划规则。全局提示词为空、超长或解析失败时使用内置默认值，不能因此关闭普通对答或让设备执行未授权工具。

主动规划的记忆范围采用受限的混合检索，而不是完整历史回放。默认读取最近 12 个已完成对话轮次、最近 3 条主动消息，以及长期 Memory 中按相关性、时间、新鲜度和未完话题排序的前 5 条结果。单次规划的上下文设置总 token 上限，超过上限时优先保留最近对话和用户明确表达的事实。普通闲聊中很久以前的低相关记忆不进入规划；被标记为重要或持续未完成的话题可以跨越时间窗口保留。召回结果必须带来源和置信度，低置信度内容不能被主动消息引用。

记忆检索失败、返回空结果或只返回低置信度内容时，主动规划仍可运行，但只能选择保持安静或基于当前连接内最近一句话生成极短回应，不能猜测用户经历。主动消息写入 Memory 时保留 `source=proactive`、引用的记忆 ID 和规划时间，后续规划用这些字段做去重和冷却。

全局提示词的默认内容应表达以下约束：主动陪伴的目标是适时提供自然、克制的陪伴，不是维持聊天时长；没有自然切入点就保持安静；优先回应近期情绪、未完话题、明确计划和真实生活细节；不得固定重复“你在干嘛”“还好吗”等问候；不连续追问，不强行延续对话；只能引用真实上下文，不得编造共同经历；不说教，不制造焦虑，不诱导依赖；主动内容最多两句、不得超过 80 个汉字，并适合直接口播。

规划结果使用严格结构化输出，内部字段为 `action`、`text`、`emotion` 和 `reason_code`。`action` 只能是 `speak` 或 `silent`，选择 `silent` 时 `text` 必须为空。`reason_code` 使用有限枚举，不保存自由发挥的分析文本。服务端规则要求模型只返回该结构，禁止把规划理由、提示词和记忆原文播给用户。

主动规划不得主动暴露密码、令牌、财务信息、医疗细节、第三方隐私或用户没有明确要求记住的敏感内容。用户刚刚主动谈过的敏感话题可以在同一轮对话中回应，但不应在数分钟后的主动问候里突然回访。

## 失败处理

噪声分类失败时按噪声处理，不触发主动回复。VAD、ASR 或 Memory 暂时不可用时，主动规划暂停，普通对答继续可用。LLM 规划超时、返回无效结构或超过长度上限时，丢弃本次主动消息并进入退避，不播放错误文本。TTS 失败时清理当前句子的音频队列并恢复监听，不能阻塞下一次用户输入。

用户在主动规划或播放期间说话时，优先保障用户接管。所有等待任务和正在进行的 LLM/TTS 操作都必须可取消，旧任务不能在取消后继续发送音频或写入新的主动消息。

## 验收与测试

Java 测试覆盖数据库默认值、模式合法性、管理员权限、审计事件、全局主动提示词保存、默认回退、配置版本和设备不支持主动模式时的拒绝。控制台测试覆盖设备列表和详情的模式展示、系统设置中的提示词加载和保存、保存成功、保存失败和旧值保留。

Python 测试覆盖噪声不刷新活动、短促人声刷新活动但不触发回复、规划期间活动取消、生成后播放前的代次检查、普通对答与主动规划互斥、主动规划提示词分层、记忆数量和 token 上限、低置信度记忆导致保持安静、无效 LLM 结构退避和 TTS 失败恢复。

固件和网关测试覆盖 realtime+Aec 收音、播放中插话、前滚音频、模式配置下发和断线重连。真实设备验收至少覆盖安静环境、扬声器播放残音、键盘敲击、桌面碰撞、风噪、咳嗽、嗯声、短句插话、规划期间插话、错误哈希式配置回退和设备重启恢复。验收记录必须带设备 ID、板型、固件版本、Agent 版本、模式、VAD 事件、ASR 结果和 TTS 状态。

## 实施边界

第一阶段只实现设备级模式字段、管理端设置、配置下发和主动循环的最小闭环。空闲阈值、退避、字符上限和 AEC 能力由服务端配置控制，暂不开放复杂的时间段、情绪模型和多设备联动。Skill 工具、动态唤醒词、NVS 和分区发布不在本轮默认改动范围内。
