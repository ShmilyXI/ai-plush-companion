# AI Plush Companion 链路与平台收敛计划

## 文档目的

这份文档是后续工程工作的共同基线。它记录当前代码已经形成的真实边界、目标链路、改造顺序、验收证据和清理规则，避免在跨 Java、Python、MQTT、固件和管理端工作时丢失最初约束。

本计划采用证据优先、分阶段收敛的方式。先保证现有设备链路可观测、可复现、可回归，再抽象面向 APP、小程序和网页的通用对话能力，最后处理历史代码和旧管理台。任何清理都必须建立在引用确认和回滚准备之上。

## 当前范围与事实

仓库由 ESP32 固件、`mqtt-gateway`、Python `xiaozhi-server`、Java `manager-api`、新版 `companion-console` 以及仍需核查的历史前端组成。项目约定要求板级差异留在 `firmware/main/boards/<board>`，通用设备能力留在 `firmware/main`，设备能力由设备上报和服务端投影共同决定。

当前设备对话入口是 WebSocket 协议。设备也可以通过 MQTT+UDP 连接，MQTT 网关在设备认证和 `hello` 后建立到 Python 服务的 WebSocket 桥接，接收 UDP 音频并封装为 WebSocket 二进制帧，同时把 Python 的下行音频拆回 UDP，把 JSON 控制消息转回 MQTT。证据位于 `mqtt-gateway/app.js` 的 `WebSocketBridge`、`MQTTConnection` 和 UDP 收发逻辑。

Python 的每连接运行时由 `core/connection.py:ConnectionHandler` 持有。二进制音频进入 `core/handle/receiveAudioHandle.py`，先经过 VAD，再进入 ASR。识别完成后，`startToChat` 处理意图、绑定状态、输出限制和打断逻辑，并提交 `ConnectionHandler.chat`。`chat` 会加载当前连接的 Agent 能力快照、记忆、身份、Skill 工具和系统提示词，调用 LLM 的流式接口，把可见文字写入 TTS 队列。`core/handle/sendAudioHandle.py` 负责音频流控、打断和下行传输。

Java `manager-api` 当前承担用户、设备绑定、角色和 Agent 快照、模型资源、音色资源、记忆、Skill、MCP、能力投影、调试日志和 OTA 等控制面职责。新版 `companion-console` 已把普通用户工作台和管理员资源管理分开。`docs/unify-agent-configuration-progress.md` 记录了 Agent 版本化配置和能力隔离的现状，也明确记录了真实业务数据库迁移、真实 Memory 服务和部分回滚健康检查尚未完成。

当前 Python 的 `/xiaozhi/internal/playground` 是受保护的虚拟设备测试入口，使用事件流模拟设备输入输出。它不是面向外部 APP 的生产对话 API。

本轮已确认存在一台真实设备，设备串口为 `/dev/tty.usbmodem2101`。后续真实验收必须以该设备或同等能力设备为证据来源，不以模拟测试替代硬件链路验证。

## 标准链路

标准设备链路必须保持以下顺序和职责边界：

```text
设备麦克风
  -> 固件采样、编码、发送
  -> MQTT+UDP 网关或直连 WebSocket
  -> Python WebSocket 会话
  -> 音频解码、AEC（启用时）、VAD
  -> ASR 流式或分段识别
  -> 意图与打断判定
  -> 会话编排器加载 Agent 快照、系统提示词、记忆和工具
  -> LLM 流式响应
  -> 文本分句和 TTS 队列
  -> TTS 流式合成
  -> 音频流控与下行传输
  -> MQTT 网关或 WebSocket
  -> 固件解码并由扬声器播放
```

文字流和音频流必须共享同一个会话、轮次和 `sentence_id`。一轮对话的取消、设备插话、LLM 失败、TTS 失败或连接断开都必须能终止该轮的剩余工作，不能把上一轮音频泄漏到下一轮。

## 目标架构

设备协议和外部应用协议分开。MQTT+UDP 继续作为硬件接入协议，负责设备身份、低延迟音频、设备控制和设备 MCP 能力同步。APP、小程序和网页使用独立的外部会话接口，建议以 HTTPS 创建会话，以 WebSocket 或 SSE 接收流式事件，并以二进制音频或可约定的音频数据格式返回 TTS。两类入口最终汇聚到同一个 Python 会话编排核心，而不是让 APP 伪装成设备连接 MQTT。

外部会话请求至少需要包含输入类型（文字或音频）、角色模板或 Agent ID、可选模型和音色引用、会话 ID、客户端请求 ID以及流式能力声明。服务端必须根据调用方权限解析资源引用，不接受浏览器直接传入 provider 密钥，不允许调用方绕过 Agent 已发布版本和工具隔离。

角色配置的有效来源保持单一方向：管理端保存草稿，发布生成不可变版本，激活确定设备或外部会话使用的版本，Python 连接在建立时固定版本快照。角色身份、系统提示词、性格、模型、音色、记忆策略和 Skill 都从该快照解析，不能由 Python 本地默认值覆盖已经明确的设备级或会话级配置。

## 分阶段改造

### 阶段一：现状基线与端到端证据

目标是把当前设备链路跑通并留下可复核证据，不改变协议和业务行为。

需要完成设备固件、MQTT 网关、Python WebSocket、Java 配置拉取和新版管理台入口的调用关系图；记录一次真实设备从收音到扬声器播放的完整时间线；确认 ASR、LLM、TTS 实际 provider、模型、音色、提示词来源和 Agent 版本；确认取消、插话、断网、provider 超时、无声音超时和设备重连的现有行为；补齐链路日志中的 `session_id`、`sentence_id`、设备 ID、Agent 版本和 provider 标识。

阶段出口是：真实设备完成至少一轮文字可辨识、音频可播放的对话；每个环节都有成功或失败事件；没有发现配置来源不明、跨设备工具串线、旧音频残留或连接关闭时任务泄漏。

### 阶段二：链路职责收敛与健壮性

目标是让每层只承担自己的职责，并把失败处理变成可测试的契约。

Python 侧把音频接入、会话编排、provider 适配、工具执行和流式输出的接口进一步收敛，优先处理 `ConnectionHandler` 中跨职责耦合、线程池与事件循环交叉、TTS 队列清理、LLM 流中断和错误响应一致性。MQTT 网关侧确认认证、重连、序列号、UDP 加密、重复 `hello`、音频丢包和桥接断开行为。Java 侧确认配置发布与 Python 拉取之间的版本、缓存失效和失败回退。

阶段出口是：每种主要失败都有稳定的错误码或可读提示；断开和取消后不会继续发送音频；设备 A 的 Agent、工具和记忆不会出现在设备 B；旧 Agent 版本不会被在线连接中途替换。

### 阶段三：统一外部对话 API

目标是为 APP、小程序、网页和第三方调用方提供与设备无关的对话入口。

先定义版本化的会话、输入、流式事件、音频块、错误、取消和结束协议，再实现 Java 鉴权和资源授权、Python 会话编排适配、外部 WebSocket 或 SSE 出口。文字输入必须可直接返回流式文字；音频输入必须经过同一套 ASR、LLM 和 TTS 编排；调用方可以引用角色模板、Agent 版本、音色和模型，但不能提交任意 provider 配置或工具代码。角色列表、模型列表、音色列表、设备列表和会话历史作为独立的只读或受权限保护资源接口提供。

阶段出口是：不连接 MQTT 的客户端可以完成一轮文字对话和一轮音频对话；输出事件可以关联会话和请求；取消、重试、幂等和配额限制有契约测试；设备链路行为不受外部 API 引入影响。

### 阶段四：角色配置逐项实效验证

目标是证明管理端配置不仅保存成功，而且真正进入运行时链路。

按角色模板、系统提示词、性格、LLM 模型、ASR 模型、TTS 模型、音色、记忆策略、Skill 和设备绑定逐项建立验证用例。每项验证都必须记录管理端保存值、发布版本、Python 拉取的有效配置、provider 实际请求参数以及最终文字或音频表现。验证必须覆盖修改后新连接、旧连接保持旧快照、发布失败保留上一版本、资源不可用时拒绝激活和设备能力不足时过滤工具。

阶段出口是：每个角色配置字段都有一条从管理端到运行时和最终输出的证据链；发现配置不生效时可以定位在持久化、发布、拉取、合并、provider 适配或输出环节。

### 阶段五：历史代码和旧管理台清理

目标是移除明确无用的历史实现，不以猜测删除仍承担兼容职责的代码。

先生成 Java、Python、MQTT、固件和前端的引用清单，区分生产路径、兼容路径、测试路径、脚手架和历史副本。旧管理台只有在新版 `companion-console` 覆盖其路由、接口和部署入口，并完成构建与回滚验证后才能删除。小智来源代码的改名和语言统一按模块逐步处理，保留必要的第三方许可证和来源说明，不把可执行 Plugin 或 MCP 密钥暴露到管理端或浏览器。

阶段出口是：删除项有引用证据、替代实现、测试覆盖和回滚方式；构建产物不再包含旧前端；服务端启动、设备 OTA、MQTT、管理台和外部 API 的健康检查均通过。

## 健壮性与观测要求

每个连接和每轮请求必须有可关联的标识。日志默认记录阶段、耗时、状态和错误类型，不记录 API 密钥、MCP 密钥、完整音频和不必要的用户隐私。链路至少需要记录音频首帧、VAD 起止、ASR 首个稳定文本、LLM 首个可见 token、TTS 首包、设备首个播放包、取消原因和最终状态。

所有流式阶段都需要超时、取消和背压策略。ASR、LLM、TTS provider 失败时要有明确的降级或可读错误；TTS 队列和音频流控必须支持清空；网络重连不能复用已经失效的会话快照；外部会话必须有并发、速率和输出大小限制。记忆读写失败不能破坏当前对话，但必须留下可观测事件。

## 验收矩阵

验收分为静态、契约、集成和真实设备四层。静态层运行 Java、Python、MQTT 和控制台现有测试、类型检查、Lint、构建及 OpenSpec 校验。契约层验证 Agent 版本、模型和音色引用、设备工具隔离、密钥脱敏、外部 API 事件格式和幂等。集成层使用模拟 provider 验证完整文字和音频流、取消、重试、超时、断线和回滚。真实设备层验证收音、VAD、ASR、模型回复、TTS 播放、插话、音量、状态上报、MQTT 重连和设备重新上线。

动态唤醒词、NVS、分区和刷写保护不属于本轮链路重构的默认改动范围。涉及固件发布时必须继续遵守项目既有的布局 2、assets 成套发布和保留 NVS 规则。

## 变更纪律

每个阶段开始前先补文档中的证据和验收用例，再修改实现。跨层协议、配置字段和数据库结构必须先有版本化契约。删除代码前先确认生产引用、测试引用、部署引用和回滚路径。任何真实设备验证都必须记录板型、固件版本、应用版本、Agent 版本、分区信息和测试结果，不能用另一块板子的固件替代目标设备。

本计划只定义方向和验收边界，不授权一次性重写。后续每个具体改动都应从本计划中选定一个阶段和一个可独立验证的切片。

## 第一项执行任务

下一步先完成阶段一的现状基线：读取真实设备当前板型和应用版本，确认串口对应关系，采集一次完整对话的设备、网关、Python 和 Java 日志，整理出实际 provider、Agent 版本、音色和提示词来源，然后把结果回填到独立的链路验收记录中。未完成这项基线前，不删除历史代码，不调整 MQTT 协议，不开放外部生产 API。
