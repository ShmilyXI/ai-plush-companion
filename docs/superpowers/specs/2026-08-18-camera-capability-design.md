# 摄像头能力恢复设计

## 背景

当前固件版本为 2.2.7，`zhengchen-cam` 已包含官方小智 2.2.4 的 `Esp32Camera` 实现，包含 RGB565 编码缓冲和 JPEG 上传链路。飞书文档提到的 2.0.5 至 2.2.2 摄像头问题不适用于当前代码，因此不做整仓升级。

当前失败发生在两层。固件的 `ZhengchenCamBoard` 没有在设备信息中上报 `has_camera`，摄像头初始化失败时仍会保留一个非空对象。服务端启用后台能力配置时，没有命中已绑定 Skill 的请求只暴露 `handle_exit_intent`，仓库也没有内置摄像头 Skill，导致 `self.camera.take_photo` 虽然由固件注册，却不会进入模型可见工具集合。

## 目标

让征辰摄像头设备在后台配置模式下，用户说出拍照、相机、摄像头或查看画面等请求时能够看到并调用设备拍照工具。设备能力列表要准确反映摄像头是否初始化成功，初始化失败时不能把不可用摄像头报告为可用。

## 非目标

不迁移官方 2.4.x 全部固件，不替换征辰板的音频、显示或电源实现，不绕过已有服务端 MCP、Plugin 或 Skill 授权，不修改视觉接口协议和图片上传格式。

## 设计

固件在 `Camera` 接口增加只读的就绪状态查询，`Esp32Camera` 在 `esp_camera_init` 成功后置为就绪，失败时保持未就绪。`zhengchen-cam` 的 `GetCamera()` 只返回就绪实例，并在 `GetBoardJson()` 中上报 `has_display` 和 `has_camera`。这样设备注册、激活和管理后台展示使用同一份真实状态，拍照工具也不会由失败的初始化对象继续提供。

服务端保留能力中心的默认关闭策略，但在没有激活 Skill 的普通对话中，对设备本地 MCP 工具做一组窄范围的关键词路由。拍照、相机、摄像头、照片和查看画面只允许 `self_camera_take_photo`，音量、亮度和屏幕控制继续沿用现有设备工具命名。该路径只读取连接已经上报的设备工具，不会把服务端 Plugin、远程 MCP 或未上报工具暴露给模型。已有 Skill 回合和非后台配置模式的行为保持不变。

视觉 URL 仍由服务端 MCP 初始化消息下发，固件继续使用现有 `ParseCapabilities` 和 `SetExplainUrl`。若 URL 未配置或设备无法访问，工具调用返回现有错误，不改变上传协议。

## 数据流

设备启动时初始化摄像头并记录就绪状态。设备上报 board JSON 和 MCP 工具快照，管理后台据此保存 `has_camera` 与 `self_camera_take_photo` 可用状态。用户发起包含摄像头关键词的请求时，服务端只把已上报的拍照工具加入本轮函数列表。模型调用后，服务端通过设备 MCP 请求拍照，固件捕获图像并向已下发的视觉解释地址上传，结果沿现有 MCP 响应返回。

## 错误处理

摄像头初始化失败时不注册拍照工具，也不报告 `has_camera=true`。拍照失败、视觉 URL 未设置、HTTP 连接失败和视觉服务非 200 响应继续转换为现有设备工具错误，不泄漏底层凭据或图片内容。关键词未命中时仍只保留系统退出工具，避免扩大工具可见范围。

## 测试策略

固件侧增加静态回归检查，确认征辰板 JSON 包含 `has_camera`，并确认未就绪摄像头不会从 `GetCamera()` 暴露。服务端增加路由测试，确认后台配置模式下摄像头关键词只返回设备拍照工具，普通聊天和未上报拍照工具不会返回；已有 Skill 回合仍按白名单过滤。完成后运行服务端相关 Python 测试、固件可用的构建或编译检查，并核对最终 diff。

## 备选方案

整仓同步官方 2.4.x 会带来板级适配和依赖迁移，不能解决当前能力中心的工具过滤。新增一个需要管理员手动绑定的摄像头 Skill 能工作，但无法恢复开箱即用行为，也会让每台设备都依赖额外配置。因此采用固件状态修正加服务端窄范围设备工具路由。
