# 网页端登录

`companion-web` 面向普通用户，用手机号加短信验证码登录。本文记录登录、邀请制和会话续期的约定。

## 登录方式

网页端有两种进入方式。

登录页分“登录”和“注册”两个标签，和 App 共用同一套账号：

- **注册**：手机号、短信验证码、密码、邀请码，加上勾选同意协议。密码 8 到 32 位，同时有大写字母、小写字母和数字，浏览器里用 SM2 加密后才发出去（公钥经 `/api/auth/pub-key` 取自 manager-api 的 `/user/pub-config`）。调 `/app/v1/auth/register`，成功后直接登录。
- **登录**：默认用手机号和短信验证码（`/app/v1/auth/login-code`），也可以点“用密码登录”改用手机号和密码（`/app/v1/auth/login-password`）。密码登录时点“忘记密码？用验证码登录”切回验证码。
- 用验证码登录一个还没注册的手机号，服务端回“手机号码未注册”（10071），验证码不作废。登录页转到注册标签，手机号和验证码都带过去，用户只需要设密码和填邀请码。注册时手机号已经有账号（10070），转回登录。
- 以前用验证码直接登录建的账号没有密码，用密码登录时提示“这个账号还没有设置密码，请用验证码登录”。登录后在个人中心的“账号安全”里点“设置密码”补设；有密码的账号这里是“修改密码”。两种都分两步：先验证手机号，给自己的手机发验证码（`/app/v1/auth/account/sms-code`）并核对（`/app/v1/auth/account/verify-code`，验证码不作废，输错照样计数）；对了才进入设新密码的页面，保存时带着同一个验证码和 SM2 加密的新密码调 `/app/v1/auth/account/password`。所以忘了旧密码也能改。个人资料接口返回 `hasPassword`，不返回密码本身。

管理员从管理台进入时，管理台签发一次性登录码，网页端用它换一个 15 分钟的短期会话。这种会话不能续期，过期后回到登录页。

管理台有两个入口：菜单里的“网页端”（`/web`）把网页端嵌在页面里，“在新窗口打开”和概览页上的按钮在新窗口里打开。

- 嵌在页面里时，网页端加载好后向管理台发 `companion.ready`，管理台收到后才向后端要登录码，用 `companion.bootstrap` 发回去。不能在 iframe 的 load 事件里发：那时网页端还没开始监听，码会被丢掉。网页端在里面刷新会再发一次 `companion.ready`，每次换一个新码。
- 新窗口打开时，登录码放在地址的 `code` 参数里，网页端换完后把它从地址里去掉。浏览器拦掉弹窗时，在当前窗口打开。
- 网页端只接受 `NEXT_PUBLIC_CONSOLE_ORIGIN` 里列出的管理台地址发来的消息，可以写多个，用逗号分隔。后端只给 `COMPANION_WEB_ALLOWED_ORIGINS` 里的网页端地址签发登录码。
- 嵌在页面里时，网页端的登录 Cookie（`SameSite=Lax`）只有在网页端和管理台“同站”时才会被带上，否则网页端一直显示“未授权”。公网部署时两者要放在同一个主域名下，例如 `console.example.com` 和 `app.example.com`。本机开发时 `localhost` 和 `127.0.0.1` 算两个站，所以两边都是本机地址时，管理台会让网页端用和自己相同的主机名。

从管理台进入的会话可以添加、修改和清空自己的角色，退出登录和注销账号只对手机号登录的账号显示。

两种会话都放在 httpOnly Cookie 里，页面脚本读不到令牌。

## 邀请制

系统参数 `app.invite_required` 控制新账号是否必须凭邀请码创建，缺省为必须。只有明确设为 `false` 才放开；参数缺失或读不到时按必须处理。管理台的“邀请码”页面可以开关邀请制、生成和停用邀请码。

邀请制只约束新账号的创建，已有账号登录不需要邀请码。

注册时按下面的顺序检查：

1. 校验短信验证码，但不作废。
2. 手机号还没有账号；检查邀请码是否可用，密码是否符合规则。
3. 创建账号，并占用邀请码的一次名额。这两步在同一个事务里，名额被别人抢先用完时账号一并回滚。
4. 作废短信验证码，签发会话。

先校验验证码再提示“需要邀请码”，是为了不让没有证明手机号归属的人探测某个手机号是否已注册。验证码在第 4 步才作废，所以邀请码填错时可以直接改了重试，不用重新收短信。

邀请码是 8 位大写字母和数字，去掉了容易看错的 0、O、1、I、L，输入时不区分大小写。占用名额是一条带条件的 `UPDATE`，并发下不会超发。每个账号用的是哪个邀请码记录在 `ai_invite_code_use`，可以用来区分内测批次。

## 短信验证码

验证码是登录凭据，用安全随机数生成，5 分钟内有效。

同一个验证码最多允许输错 5 次，超过后作废。这样手滑输错一位不用重新收短信，暴力尝试也只有 5 次机会。

发短信前要先答对图形验证码。点“获取验证码”后弹出一个小窗口，里面是图片和输入框：登录页在浏览器里生成一个编号，经 `/api/auth/captcha?id=<编号>` 取图（转发 manager-api 的 `/user/captcha`），点“发送验证码”时把编号和图片上的字符一起交给 `/app/v1/auth/sms-code`。一张图只能核对一次，不管对错都作废：答错时窗口不关、换一张新图；因为别的原因发不出去（太频繁、号码不对）就关掉窗口，在表单里提示。只在要发短信时才取图，打开登录页不会消耗图形验证码。答错不发短信，也不占用来源地址当天的次数。已登录用户注销账号时的验证码不需要图形验证码。本机的固定验证码（`ZIXUAN_SMS_FIXED_CODE`）直接登录，不经过发短信，所以也不需要图形验证码。

发送频率有三层限制：同一手机号 60 秒一次、每天的上限由 `server.sms_max_send_count` 控制，同一来源地址每天 20 次。

### 短信通道：阿里云

验证码由 manager-api 生成、存在 Redis、由 manager-api 校验，阿里云只负责把短信送到手机上（`ALiYunSmsService`）。阿里云有两个能发验证码的接口，用系统参数 `aliyun.sms.api` 选：

- `verify`（默认）：号码认证服务的“短信认证”，接口 `SendSmsVerifyCode`（`dypnsapi.aliyuncs.com`）。可以用控制台“赠送签名配置”里的签名和赠送模板，不用自己申请签名、等报备。赠送签名必须搭配赠送模板。我们把自己生成的验证码写进模板参数 `{"code":"…","min":"5"}`，阿里云不保存它，所以不调用它的 `CheckSmsVerifyCode`。
- `sms`：短信服务，接口 `SendSms`。要用自己申请并审核通过的签名和模板，见 `server/docs/ali-sms-integration.md`。

两种都在管理台“参数管理”里填同样四个参数：

| 参数 | 短信认证的取值 |
| --- | --- |
| `aliyun.sms.access_key_id`、`aliyun.sms.access_key_secret` | RAM 用户的 AccessKey，这个用户要有号码认证服务的权限（系统策略一般是 `AliyunDypnsFullAccess`，以 RAM 控制台显示为准） |
| `aliyun.sms.sign_name` | 赠送签名，例如 `恒创联众` |
| `aliyun.sms.sms_code_template_code` | 赠送模板，登录/注册是 `100001` |

改了参数要清掉 Redis 里的参数缓存（见 `deploy/local/README.md`）或者重启 manager-api。阿里云拒绝发送时（号码格式不对、发得太频繁、签名或模板不存在），这次不计入当天的发送次数，用户看到的提示里带着阿里云的错误码，日志里有 requestId。短信认证自己也有频率限制：同一号码默认 60 秒一条，每天的上限在控制台“通用设置”里调。

### 来源地址

来源地址的限制依赖 manager-api 能看到用户的真实地址。网页端的服务端路由会把浏览器地址放在 `X-Forwarded-For` 里转发，但 manager-api 默认不信任这个头。对外部署时必须设置环境变量 `SERVER_FORWARD_HEADERS_STRATEGY=native`，让 Tomcat 只接受来自内网代理的转发头。不设置的话，所有网页用户会被当成同一个来源，全站每天只能发 20 条验证码。

### 本机调试

本机没有短信通道时，启动 manager-api 时设置 `ZIXUAN_SMS_LOG_CODES=true`，验证码会写进服务日志而不是发到手机。这个实现默认不存在，只有显式设置才会启用。任何能被外部访问的环境都不能开启，否则看得到日志的人可以登录任意手机号。

再加上 `ZIXUAN_SMS_FIXED_CODE=000000`，就有了一个固定的验证码：任何手机号都可以直接填它登录，不需要先点“获取验证码”，也不受发送次数的限制。它只在日志模式里才读取，单独设置不起作用；值必须是 4 到 8 位数字。它比日志模式更危险，知道这个数字的人不需要看日志就能登录任意手机号，所以同样只能用于本机。

本机启动的完整命令：

```bash
ZIXUAN_SMS_LOG_CODES=true ZIXUAN_SMS_FIXED_CODE=000000 java -jar target/zixuan-manager-api.jar
```

启动日志里会有两行警告，分别说明日志模式和固定验证码已经开启。

## 会话续期

手机号登录后有两个令牌：访问令牌 12 小时有效，使用中会自动顺延；刷新令牌 30 天有效。

网页端的服务端路由在访问令牌失效时用刷新令牌换一个新的，并重试刚才的请求，用户不会察觉。刷新令牌也失效时清掉 Cookie，回到登录页。所以只要 30 天内用过，就不需要重新登录。

退出登录时通知 manager-api 作废当前会话，再清掉 Cookie。

## 第一个角色

新账号没有角色。登录后如果没有可用的角色，网页端显示角色选择页，从预设模板里选一个创建。

从模板创建出来的角色直接生效：初始版本没有需要把关的改动，而对话只认已激活的版本。之后在管理台里修改角色仍然走“发布、激活”的流程。

网页端只列出有已激活版本的角色。

## 回复里的情绪标记

角色提示词要求模型在每次回复开头带一个情绪标记，供设备驱动表情。公共会话在把回复交给客户端和语音合成之前会去掉这个标记，支持 JSON 头和 `emotion: happy` 两种写法。不以 `{` 或 `emotion` 开头的回复不会被缓冲，逐段直接输出。
