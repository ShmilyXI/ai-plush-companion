# 对话用量和每日额度

每完成一轮对话记一次用量，用于核算成本、限制每人每天的对话次数，以及统计活跃情况。本文记录用量记了什么、额度怎样生效。

## 记了什么

`ai_conversation_usage` 表每轮一行，只有数量和耗时，没有对话内容。用户删除对话记录不影响这张表。

| 内容 | 说明 |
|---|---|
| 用户、角色、会话、日期 | 日期按 Asia/Shanghai 计算 |
| 是否登录用户的会话 | API Key 会话记在 Key 的所有者名下，单独标记 |
| 输入方式 | 文字或语音 |
| 模型代号 | 这一轮实际使用的对话模型 |
| 输入和输出 token | 服务商报告的数字。服务商不报告时为空，不估算 |
| 输入字数、回复字数、语音合成字数 | 总是有 |
| 首字耗时、总耗时 | 从收到输入算起，单位毫秒 |

用量由 `zixuan-server` 在一轮完成时随对话历史一起上报，manager-api 在落库前把它从历史里拿掉，所以用量不会出现在任何对话记录里。

失败的一轮不记用量。

### token 数

对话模型流式输出时，运行时在请求里带上 `stream_options.include_usage`，要求服务商在结尾报告这次的 token 数。

少数 OpenAI 兼容接口不认识这个参数，会直接拒绝请求。被拒绝时运行时去掉它重试一次，成功后记住这个接口地址，同一个进程里不再带这个参数。这种服务商的 token 数为空，管理台显示为“未知”。对话不会因为计量而失败。

## 每日额度

系统参数 `app.daily_turn_limit` 是每个登录用户每天最多对话的轮数，默认 200，设为 0 表示不限制。在管理台的“参数管理”里修改。

角色主动说的开场白（见 `docs/conversation-opening.md`）也记用量，输入方式是 `opening`，但它不是用户发起的一轮，不占每日次数。

额度在两处生效：

1. 建立会话时，manager-api 检查用户今天还剩多少轮。用完了就拒绝建立会话，返回错误码 10212。没用完时把剩余轮数（不超过单个会话的 100 轮上限）写进运行时配置的 `turnBudget`。
2. 每完成一轮，manager-api 在记完用量后把剩余轮数告诉运行时。剩余为 0 时，运行时不再开始新的一轮，返回 `daily_quota_exceeded`。

第 2 步保证同时开多个会话也不能明显超出额度：每个会话最多多出正在进行的那一轮。

已用轮数直接从用量表里数，不依赖缓存，清空 Redis 不会让额度被重置。

API Key 会话只记用量，不受这个额度约束，它们有自己的频率限制。

网页端在额度用完时显示“今天聊得够多啦，明天再来”，停用输入，并且不再自动重连。

## 查看用量

管理台的“对话用量”页面显示最近 14 天每天的活跃用户数、对话轮数、语音轮数、开场白次数、token、语音合成字数和平均首字耗时，点某一天可以看那天用得最多的用户。

对应的接口是 `GET /admin/usage/daily` 和 `GET /admin/usage/users`，需要超级管理员权限。
